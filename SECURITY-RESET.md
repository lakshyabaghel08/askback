# Secure access and one-time reset

**Status:** Applied to the AskBack project on 2026-11-01 as migration `askback_secure_reset`. The live schema was inspected before execution: the old members, goals, questions, question-subject links and study logs were removed, while the group and subjects were retained. A new confirmed owner account was linked to a new owner profile. Anonymous table access was revoked. Public signup was later enabled for the owner-approved membership flow described below. The script below is preserved for audit and is intentionally not repeatable. Deploy the updated HTML to use the new login; the old deployment cannot access the secured database. The former client-side admin password was public; consider it compromised and never reuse it.

## Reset procedure (historical; do not run again)

1. In the Supabase dashboard, make sure this is a dedicated AskBack project. Review **all schemas**, tables, foreign keys, triggers, views, functions (including SECURITY DEFINER functions outside `public`), storage buckets, Auth users, grants and RLS policies. The inspected app schema contains `groups`, `subjects`, `members`, `goals`, `questions`, `question_subjects`, `study_logs`, and the `study_log_totals` view. Identify any additional study logs, history, copies, exports or integrations. The script refuses unexpected public tables or foreign-key dependents; modify it only after reviewing those records and dependencies. Revoke or repair any additional access paths, including other exposed schemas, storage and edge functions. Do not use this script unmodified in a shared project.
2. Plan for permanent loss. The transaction deleted **all** rows in `members`, `goals`, `questions`, `question_subjects`, and, if present, `study_logs`, including inactive members and history. It recreates a single owner member. `groups` and `subjects` were preserved as app configuration. Supabase backups, point-in-time recovery, exports, storage objects, logs, and copies outside these tables are not erased by SQL; review and delete/expire them according to your retention requirements. This may require Supabase support. Do not claim permanent removal until those copies are handled.
3. In Authentication settings, disable public signups and anonymous sign-ins; configure the site's HTTPS URL and approved redirects. Use the dashboard Auth user management to create a **new** confirmed owner email/password account. Set the password privately in the dashboard, not in source code, SQL, logs or chat. Confirm the owner can sign in to Supabase Auth. Save the new Auth user UUID from the dashboard. Avoid reusing an old member account: all old mappings will be removed.
4. Verify you have database owner/SQL editor access and a recovery plan. In `supabase/reset_and_secure.sql`, replace `NULL` in the temporary config row with the new owner's quoted UUID (`'…'::uuid`) and set the display name if desired. A password is never needed in SQL. Read the full script and adapt it to the inspected schema. It is intentionally one-time and fails on an existing `askback_access` table. Run the entire script as a single SQL-editor execution. Any error rolls back the transaction; investigate rather than bypassing checks. The owner profile and mapping are created in the same transaction as the reset.
5. Delete or disable all former Auth users in the dashboard (do **not** delete the new owner), revoke their sessions, and remove any obsolete project/API/service-role credentials and integrations. The migration's authorization mapping already denies every former user, including those with an unexpired token. Never ship a service-role key to the browser. Rotate any exposed privileged credentials; the publishable key in `index.html` is not a secret and must be protected by RLS.
6. Deploy the updated HTML **after** applying the SQL. Ensure it is served over HTTPS. Browser storage holds Supabase's refresh token, so protect the hosting environment from XSS and malicious scripts. Disable public signup even though unmapped accounts are denied by RLS.

## Membership approval and removal

The `askback_member_approval` migration is applied to the AskBack project. New users register with email, password and display name, confirm their email, and return to the app. Their request is submitted on their first confirmed sign-in; until approval, RLS denies them all study data. The owner's **Admin** tab lists pending requests and active members. The owner can approve or reject requests and remove a member. Rejection and removal revoke that user's existing sessions; removal also deactivates the member and removes the access mapping without deleting study history. Rejected and removed accounts cannot submit a new request automatically; contact the owner to arrange access.

Only the confirmed owner configured in the private `askback_owner` table can call the admin functions. Direct browser access to the owner, request and access tables is denied. Never assign owner based on user-editable metadata or a display name. Keep database-owner access separate from ordinary app login.

The project URL and allowed confirmation redirect are configured for `https://lakshyabaghel08.github.io/askback/`. Deploy the updated frontend there before inviting applicants; the current changes live on the working branch until deployed. For other trusted deployment URLs, add the exact URL in Supabase Auth URL Configuration. Email confirmations remain required. No custom SMTP host is configured: Supabase's default email service is intended for testing and restricts recipients and throughput. Configure a production SMTP provider privately in the Supabase dashboard before relying on registration for arbitrary users; never put SMTP credentials in the frontend or repository.

To revoke access outside the UI, remove the user's `askback_access` mapping, mark the associated member inactive, and revoke/delete the user's Auth sessions through the dashboard. The RLS helpers also check the live membership mapping and session row on each request. A person who already viewed or exported data can retain copies.
